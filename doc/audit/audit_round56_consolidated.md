### MAJOR — GPP section strings' optional GPC segment was never stripped before bit-decoding

**File:** `lib/src/core/iab_storage.dart` (`_GppBitReader`).

**The actual bug, finally isolated after 13 rounds of "unverified" status:**
it was never the bit-*offsets* that were wrong — every offset in
`_usStateSkipBits`, `_parseGppUsNational`, and `_parseGppCalifornia` is
correct, confirmed by decoding real reference-library output end to end.
The bug was structural: a GPP section string can itself be **two
segments** — `CoreSegment` optionally followed by `.GpcSegment` (the
Global Privacy Control sub-section) — and **every reference CMP
implementation defaults to including it**. `_GppBitReader._decode()`
fed the raw, un-split string through its base64url-alphabet decoder; `.`
isn't in that alphabet, so it threw `FormatException` on essentially every
real-world two-segment string. Every one of the three callers
(`_parseGppUsNational`, `_parseGppCalifornia`, `_parseGppUsState`) wraps
that exception in a `catch` that returns `null` ("no usable signal") —
so a real CCPA/CPRA/state-privacy-law opt-out, expressed correctly by a
standards-compliant CMP (OneTrust, Sourcepoint, Usercentrics, or any CMP
built on the IAB's own reference implementation), was silently discarded
as if the user had never expressed a preference at all. This affected 15
of 21 US-state/national/California sections — including US National and
California themselves, the two most heavily fetched and most-audited
signals in this exact codebase across the last dozen rounds, none of
which had ever tested a *real*, standards-shaped two-segment fixture.

**Why this stayed hidden for 13 rounds:** every existing GPP test fixture
in this codebase (`ad_manager_core_test.dart`'s round-37 fixtures) used
single-segment strings, generated by calling the reference encoder without
setting the GPC field — technically valid GPP, but not representative of
what a real CMP actually emits by default. The bit-offset math itself was
always correct on those fixtures, which is exactly why round after round
of "re-verify the offsets" review kept coming back inconclusive or
unable to fully close the gap: the offsets were never the problem.

**Fix:** `_GppBitReader(String section) : _bits = _decode(section.split
('.').first);` — one change, in the single shared constructor every
parser routes through, so all 21 sections get it uniformly. Never reads
GPC-segment bits (irrelevant to the Sale/Sharing/TargetedAdvertising
opt-out fields each parser targets), so nothing is lost by discarding it.

**Verification:** generated a real, standards-compliant two-segment US
National fixture using the IAB Tech Lab's own `@iabgpp/cmpapi` reference
encoder (`TargetedAdvertisingOptOut=1`/Opted-Out in the Core Segment, GPC
segment appended) — `'BVQpAAAAAUA.YA'`. Added as a permanent regression
test in `ad_manager_core_test.dart`, with the exact `node -e "..."`
command in a comment so the fixture can be regenerated/audited later
(matching this file's own established convention from the round-37
fixtures). Confirmed **red** without the fix (`FormatException: invalid
GPP base64url character: 46` — `.`, resolving to `null`/no-signal instead
of the expected `true`/opted-out), **green** with it. Ran all 280 tests
across the 4 GPP/IAB-related test files plus the full 2185-test suite —
all pass, no regression.
