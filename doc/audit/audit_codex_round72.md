# Audit Round 72 — independent source audit

## Verdict

**No — not for a production app that sells, protects, or relies on VIP codes/trial entitlement as currently implemented.** The ad integration has substantial defensive lifecycle and consent machinery, and I found no source evidence of covert ad injection or revenue skimming. However, the stated zero-backend VIP model cannot provide global one-time use, Android deliberately permits unlimited reinstall trials, and a cryptographically offline-verifiable code is deliberately refused when offline. Production use is reasonable only if VIP is treated as a transferable, low-value promotion; otherwise replace it with a server-side claim/entitlement system and address the findings below. This was a static source/manifest audit; it did not exercise real provider SDK traffic, consoles, devices, or ad-policy review.

## Fraud / covert-injection conclusion — **NO EVIDENCE FOUND**

## Verified controls and limits

- Provider contract centralizes initialized state, slots, disposal hooks, reload gating and event sink (packages/ad_sdk/lib/src/core/ad_provider_adapter.dart:149-210). AppLovin auto-refresh and AdMob render visibility are explicitly modeled (same file:104-119).
- AdMob configuration sets child-directed/under-age flags and preserves test-device IDs; AppLovin reads IAB TCF before fallback consent and sets Do-Not-Sell (packages/ad_sdk/lib/src/core/ad_consent.dart:151-228). Real TCF/GPP/US-state behavior still requires console/device verification.
- Example has only network/AD_ID permissions plus public Google test ID (packages/ad_sdk/example/android/app/src/main/AndroidManifest.xml:1-6,42-47); iOS has ATT purpose and SKAdNetwork list (packages/ad_sdk/example/ios/Runner/Info.plist:48-66). SKAdNetwork completeness was not verified against current provider consoles.
- No direct HTTP telemetry/impression forwarding path was found. Revocation transport is host-supplied and CRLs are signature-verified (packages/ad_sdk/lib/src/vip/vip_revocation_provider.dart:1-36).
- Static review cannot prove native objects release, callbacks and privacy flags reach provider servers, lifecycle overlap never occurs on real devices, or account-side placement/frequency settings comply. Test Android/iOS devices, Ad Inspector/MAX debugger and publisher consoles. Google describes App Open as app-load/foreground inventory and prefers loading-screen cold-start placement: [official guide](https://developers.google.com/admob/flutter/app-open).
