## Findings, ranked by severity

### 🔴 Blocker-adjacent / Major (fix before shipping to production)

1. ~~**Android has zero anti-abuse for the 1-day trial grant.**~~ **CORRECTED after deeper investigation (see addendum below) — this finding was wrong.** The Android Auto Backup mitigation the code documents (`_first_install_guard.dart:27-47`) is genuinely implemented: `example/android/app/src/main/AndroidManifest.xml:12-15` wires `allowBackup`/`fullBackupContent`/`dataExtractionRules`, and `example/android/app/src/main/res/xml/data_extraction_rules.xml` + `full_backup_content.xml` correctly include `FlutterSharedPreferences.xml`. `README.md:1188-1249` documents the exact manifest snippet a host app must copy, plus an honest bypass matrix (Play Store reinstall same-account: **blocked**; cross-account or backup disabled: **bypassed**, disclosed). The one real residual gap: this protection is **entirely host-app-opt-in** — a consuming app that doesn't copy the example's manifest/XML gets none of it, and nothing in the SDK warns them at runtime if they haven't (unlike, say, `releaseFootgunWarnings` for other misconfigurations). That's a **minor** documentation/DX gap, not a security bug.
2. ~~**Same root cause hits VIP-code anti-replay.**~~ **Also corrected.** `_redeemed_key_ledger.dart:9-19`'s comment claims Android "intentionally has no durable backstop... for the same reason `FirstInstallGuard` doesn't" — but `FirstInstallGuard` *does* have one (Finding 1 above). The VIP redemption ledger's primary Android check lives in `AdPreferences.addRedeemedVipKeyId`/`isVipKeyIdRedeemed` (`ad_preferences.dart:276-289`), backed by the same `SharedPreferences` → `FlutterSharedPreferences.xml` file the existing Auto Backup rule already covers — so a host app that wires the Finding-1 manifest config gets this protection "for free" too. The comment is stale/inaccurate (should say "covered transitively by the same Auto Backup wiring," not "no backstop"), which is worth a doc fix, but there is no missing protection here either.
3. **App Open ads can be shown stale, past Google's ~4h freshness window.** The `isAdFresh` check (`admob_adapter.dart:596-599,611-620`) only runs inside the *load* path's "reuse existing ad" branch. `showAppOpenAdOnResume` (`ad_manager.dart:2695-2722`) shows straight from `appOpenSlot.isReady` with **no freshness check at show time**, and `_retryRefillAds` (`ad_manager.dart:3727-3729`) only reloads `idle`/`cooldown` slots, never a `ready` one — so an ad that's been sitting loaded for hours (app backgrounded a long time, resumed) can be shown well past the policy window.
4. **`showAppOpenAdOnResume` bypasses safety caps outside the one contractually-allowed case.** `ad_manager.dart:2719-2722,2739-2742` always calls `showAppOpenAd(bypassSafety: true, ...)` — not only the splash flow. This repo's own `CLAUDE.md` states the bypass is for **"the splash App Open ad"** only. The resume path re-implements *timing* gates (`ad_safety_config.dart:518-582`) but skips the daily/hourly/session cap and CTR-fraud pause entirely, while still incrementing the shared counter (`recordFullscreenAdShown()`, line 2618) — so resume-triggered App Open impressions count toward the cap but can never be blocked by it. Asymmetric, and a real ad-frequency-policy risk if a user backgrounds/foregrounds repeatedly.
5. **AppLovin banner/MREC widgets leak their native ad view on normal disposal.** `applovin_adapter.dart:148-153` (`disposeBannerInstance`) and `:212-217` (`disposeMrecInstance`) dispose only the Dart-side `AdSlot`/listenables/`ValueNotifier` — they **never call `_bridge.destroyWidgetAdView(id)`**. That native teardown only happens on full adapter reinit or app-resume reload. Every `BannerAdWidget`/`MrecAdWidget` that permanently unmounts (user navigates away for good) leaks the native `MaxAdView` object on the AppLovin side. (AdMob's equivalent `disposeBannerInstance` at `admob_adapter.dart:204-209` is correct — this is AppLovin-specific.)
6. **`showAppOpenAd(bypassSafety: true)` is a public, unrestricted API**, not scoped to the splash use case at the type/API level — nothing stops any host code from calling it repeatedly with no rate-limiting (`ad_manager.dart:2544-2611`). Finding 4 above is one concrete way this already happens *inside the SDK itself*.
7. **ATT-before-UMP/ads ordering is enforced only by a log warning, entirely opt-in on the host's splash screen.** `ad_manager.dart:2154-2165` — `initialize()`'s `autoRequestUmpConsent` path never calls `requestAtt()` itself; a host that forgets to wire `requestAtt()` into their splash simply never shows the ATT prompt, with nothing at the SDK level catching or blocking it. Revenue/attribution-losing rather than a hard legal block (native SDKs still gate IDFA on ATT status), but easy to ship wrong silently.
8. **The published pub.dev 2.0.4 is functionally behind this repo — including one security fix.** `CHANGELOG.md`'s `[Unreleased]` section (~280 lines) contains 13 already-implemented features (Rewarded Interstitial ad type, `RemoteAdSafetyProvider`, `experimentBucket`/`pickProviderCohort`, VIP revocation list, compliance-report export, `FillRateBaselineMonitor`, etc.) **and** the 2026-08-16/17 security/stability fix batch (CRL/VIP-key domain-separation vulnerability fix, stale-watchdog fix, connectivity-race fix), none of which have shipped — `CHANGELOG.md` shows 2.0.4 itself was "Docs-only. No code changes." **A production app pulling `applovin_admob_sdk: ^2.0.4` from pub.dev today does not get the security fix that already exists in this repo.**
9. **MIGRATION.md omits guidance for all three of 2.0.0's own stated breaking changes** (`autoRequestUmpConsent` default `false→true`, VIP key format `AVP1→AVP2`, `maxVipStackDuration` default `null→90 days`) — a host upgrading from 1.x has no migration guidance for any of them, and the file's FAQ still claims "2.0 is currently unreleased" though 2.0.4 has shipped.

### 🟡 Minor (worth fixing, not blocking)

10. `AdManager.loadRewardedInterstitialAd()`/`showRewardedInterstitialAd()` silently no-op under the AppLovin provider (that ad type doesn't exist on AppLovin MAX) with no host-facing warning — `shown:false` is indistinguishable from an ordinary not-ready failure.
11. If the connectivity plugin's own `initialize()` throws/times out, the SDK permanently falls back to optimistic `isConnected=true` for that session — no crash, ad loads still fail-fast safely via their own checks and a 5-minute poll backstop, but the fast-reconnect path and any host UI bound to `isOfflineListenable` go dark for the rest of the session.
12. AVP2's bundle-id binding (leak mitigation) **fails open**: if `PackageInfo.fromPlatform()` throws, `signed_vip_key.dart:216-221` proceeds with the binding check skipped entirely rather than rejecting.
13. Clock-rollback trial/VIP protection has one narrow, self-limiting gap: a device whose clock is already skewed *before the app is ever first opened* has no prior high-water-mark to clamp against. Cannot be exploited to extend/repeat a trial already observed as expired — one-time-only edge case.
14. Revoking consent (`setConsent`) updates provider flags going forward but doesn't retroactively discard already-loaded/cached ad creatives — matches both networks' own SDK limitation, but is undocumented here.
15. `ConsentManager.reset()`'s doc comment says it does *not* auto-apply provider defaults; the code actually does (the safer behavior) — stale/contradictory doc, not a functional bug.
16. No inline "replace before shipping" comment at the example app's ad-unit-ID declarations (`example/lib/main.dart:157-166`) — the only real-world safety net is a runtime release-build warning (`ad_manager.dart:147-165`), which fires too late (post-code-review) to be a great first line of defense.
17. No README/MIGRATION.md guidance on ad-placement policy (accidental-click adjacency, not auto-showing interstitials mid-critical-flow) and no layout-level enforcement anywhere in `lib/src/widget/` — entirely left to the integrator with zero guardrail.

### 🟢 Confirmed correct / production-grade (no action needed)

- **Provider/platform parity:** all 49 methods of the shared `AdProviderAdapter` interface are genuinely implemented (not stubbed) on both `AdMobAdapter` and `AppLovinAdapter`; the two intentional divergences (rewarded-interstitial unsupported on AppLovin; AppLovin init aborts for COPPA-restricted users since MAX 4.x dropped that API) are loudly logged, not silent.
- **Offline/online resilience:** every network-touching `await` in `initialize()` and the connectivity path is `.timeout()`-bounded; ad loads check `isConnected` and fail fast rather than hang when offline; the generation-token guard on `_startConnectivityWatch` (from the 08-16 audit round) holds under overlapping-call races; reconnect correctly refills all 4 ad types without an app restart.
- **VIP-by-code cryptography:** genuinely offline-verifiable Ed25519 via the `cryptography` package, private key never ships, no insecure fallback verification path exists — a decompiled binary cannot forge a valid key. The CRL/AVP1/AVP2 cross-format replay vulnerability fixed in the 08-16/17 round was independently re-verified here and holds.
- **VIP/trial expiry and CRL revocation:** fully offline after initial redemption (zero further network calls needed to keep suppressing ads for the grant's duration); CRL refresh correctly fails open (a network outage never breaks an already-active VIP or blocks a legitimate redemption).
- **Rewarded-ad integrity:** the reward is granted only from the real `onUserEarnedReward`/AppLovin reward callback on both providers — no path grants it optimistically.
- **AdMob banner disposal, all `ValueNotifier`/`Timer`/`StreamSubscription` cleanup in the 3 ad widgets, and `AdSlot.dispose()`** — all correct, no leaks found (contrast with Finding 5, which is AppLovin-specific).
- **Anti-fraud engine:** real session/hourly/daily caps, 60s fullscreen throttle, CTR-anomaly detection, click-spam detection, progressive cooldown (30min→24h doubling), `dryRun` hardened against being smuggled into a real release build — this is a genuinely above-average built-in safety layer for an ad-mediation SDK.
- **GDPR/CCPA:** correctly wired to both providers (UMP + AppLovin CMP + `RequestConfiguration`/`AppLovinPrivacySettings`); debug consent geography is release-gated and cannot ship live; UMP failures fail safe (never fail open).
- **Documentation accuracy (sampled):** every README claim checked against code (safety-cap defaults, `FirstInstallVipGrace.auto` duration, `maxVipStackDuration`, `autoRequestUmpConsent` default) matched exactly.
- **Example app:** a genuine, complete reference integration — dedicated demo pages for all 4 ad types + VIP redemption + consent flow, depends on the local package via a path dependency (tests real current source), deliberate simplifications are honestly flagged with `// ponytail:`-style comments rather than hidden.

## Recommendation: should we ship this SDK to production?

**Updated after the fix pass (2026-08-19, same day):** Findings 3, 4/6, and 5 are now fixed on `main` (commits `6ca3d78`, `05326ed`, `5fb7a58`), and Findings 1-2 were retracted as inaccurate on closer inspection (see addendum above). The picture is meaningfully better than the initial pass suggested:

1. **If pulling from pub.dev (`^2.0.4`): still no, unchanged.** You'd ship without the 08-16/17 CRL/VIP-key security fix, this round's 3 fixes, and 13 features already in this repo. Publish a new version first, or `dependency_override` to a git ref of `main`.
2. **At `main` HEAD as of this fix pass:** the two real policy/leak risks originally flagged (App Open staleness + safety-cap bypass on resume, AppLovin banner/MREC native-view leak) are fixed and test-covered (857/857 passing, 0 analyzer issues). The Android trial/VIP-replay concern turned out to be a documentation-accuracy issue in the audit, not a code gap — the mitigation already exists and is documented; the only remaining ask there is a **minor** DX improvement (nothing warns a host app at runtime if they forgot to copy the backup manifest config).
3. **Remaining open items**, none blocking: ATT-before-UMP ordering enforced only by a log (Finding 7 in the original numbering), consent-revoke not retroactively affecting cached ads, the rewardedInterstitial-on-AppLovin silent no-op, and the documentation gaps (MIGRATION.md missing 2.0.0 breaking-change guidance, stale doc comment in `_redeemed_key_ledger.dart`). Fix opportunistically.

**Bottom line:** after this fix pass, `main` HEAD is in materially better shape than pub.dev `2.0.4` and no longer has a blocking finding from this audit round. Recommended path: publish a new version bundling the 08-16/17 batch + this round's 3 fixes, then production traffic is a reasonable call.
