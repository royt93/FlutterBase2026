# Round 23 (codex) — ad plumbing, provider parity, policy

## 1. MAJOR — Rewarded completion still fires before dismissal on both providers

**What breaks:** The public `showRewardedAd` completion is treated as the end of the fullscreen lifecycle, but both adapters deliver an earned result directly from the provider's reward callback. AdMob sets `earned` and calls `fire(...)` in `onUserEarnedReward` (`lib/src/adapters/admob_adapter.dart:1390-1399`), before its dismissal callback clears the ad and moves the slot to idle (`lib/src/adapters/admob_adapter.dart:1348-1354`). AppLovin does the same in `onAdReceivedRewardCallback` (`lib/src/adapters/applovin_adapter.dart:1325-1346`), while `onAdHiddenCallback` performs the later dismissal transition (`lib/src/adapters/applovin_adapter.dart:1302-1307`). The manager consequently clears `_rewardedInFlight`, emits the reward, and invokes the host's `onEarnedReward` from this pre-dismiss callback (`lib/src/core/ad_manager.dart:4847-4867`). A host that navigates, opens a purchase/result dialog, or starts another flow in `onEarnedReward(true)` does so while the provider's fullscreen view controller/activity is still presented. The slot mutex happens to reject another SDK fullscreen ad, but it cannot prevent arbitrary host UI from being presented against the ad overlay. This is the same callback-order assumption as the just-fixed refill defect; the new refill at dismissal does not fix the public lifecycle completion.

**Concrete scenario:** A rewarded creative grants its reward, then plays an end card. GMA/AppLovin fires the reward callback; the game receives `onEarnedReward(true)` and immediately pushes its reward-result route or dialog. The ad remains onscreen until the user closes the end card. On iOS this is especially risky because both surfaces are modal view controllers; presentation can fail, be delayed, or appear immediately after ad dismissal in an unintended state.

**Smallest correct fix:** Store the earned `RewardResult` in the adapter but do not resolve `onDone` from the reward callback. Resolve exactly once from `onAdDismissed`/`onAdHidden`, after clearing the native ad and calling `markDismissed()`, using the stored earned result or `skipped`. Keep failure/show-watchdog paths resolving immediately with `skipped`. Apply the same rule to AdMob rewarded-interstitial (`lib/src/adapters/admob_adapter.dart:1541-1587`). Add ordering tests that assert the host callback is absent after reward and fires only after dismissal for both providers.

## 2. MAJOR — Displayed-but-skipped rewarded ads evade every fullscreen frequency counter

**What breaks:** `RewardResult` already distinguishes `shown` from `earned` (`lib/src/core/ad_provider_adapter.dart:12-43`), but normal rewarded adapters return the shared `skipped` result when a displayed ad is dismissed without earning (`lib/src/adapters/admob_adapter.dart:1348-1354`; `lib/src/adapters/applovin_adapter.dart:1302-1307`). The manager then records `recordFullscreenAdShown()` and the per-placement count only when `result.earned` is true, and reports the show event's success as `result.earned` (`lib/src/core/ad_manager.dart:4847-4866`). Reward eligibility is not an impression signal. A user can therefore repeatedly open and close rewarded ads before the reward point without consuming global/session/per-placement pacing. This creates an avoidable invalid-traffic/policy surface and makes compliance telemetry undercount real fullscreen displays.

**Concrete scenario:** A user taps “watch ad”, lets the rewarded creative reach the screen, closes it after a few seconds, and repeats. Each impression was actually displayed and can generate impression/revenue/click events, but the SDK records none of them toward fullscreen caps because `earned == false`. The UI remains eligible as soon as the next ad refills, allowing a rapid loop that the configured safety limits were intended to stop.

**Smallest correct fix:** Track `shown` independently: set it on `onAdShowedFullScreenContent`/`onAdDisplayedCallback`, return `RewardResult(shown: true, earned: false)` on dismissal without reward, and in `AdManager` call `recordFullscreenAdShown()`, `recordPlacementAdShown()`, and set `AdShowEvent.success` from `result.shown`; grant and emit the reward only from `result.earned`. Do the same for rewarded-interstitial, whose manager currently also counts only earned results (`lib/src/core/ad_manager.dart:4990-5007`).

## 3. MAJOR — App-open hard caps can release and refill a slot while the live ad still owns the screen

**What breaks:** `AdSlot` explicitly disarms the generic show watchdog once display is confirmed because force-releasing a displayed ad can stack a second fullscreen over it (`lib/src/state/ad_slot.dart:256-265`, `lib/src/state/ad_slot.dart:292-297`). Both app-open implementations reintroduce exactly that hazard with unconditional wall-clock hard caps. AdMob fires after 90 seconds (`lib/src/adapters/admob_adapter.dart:387`, `lib/src/adapters/admob_adapter.dart:982-1004`), disposes the captured ad, changes the slot to cooldown, and resolves the manager callback even though it has no evidence of dismissal. AppLovin similarly force-fails at its 90-second cap regardless of lifecycle state (`lib/src/adapters/applovin_adapter.dart:1009-1017`). The manager's callback always requests a replacement (`lib/src/core/ad_manager.dart:4240-4253`), so the slot can become ready while the original native fullscreen or its click-out flow is still active.

**Concrete scenario:** The user taps an app-open ad and spends more than 90 seconds in the App Store/browser, or an accessibility user simply keeps an end card open for longer than the cap. The timer fires in the background, declares dismissal, and starts a refill. When the user returns, a late native callback is ignored as belonging to the timed-out cycle; a later resume can present the replacement although the SDK never established that the original presentation was actually dismissed. On AdMob the code also calls `dispose()` on the ad while its fullscreen content may still be presented (`lib/src/adapters/admob_adapter.dart:991-1002`), an unsafe native lifecycle operation.

**Smallest correct fix:** Never force-release a display-confirmed app-open solely on elapsed wall time. Keep a watchdog only for the pre-display confirmation gap. After display, recover only from authoritative provider dismissal/failure, or from a lifecycle signal that proves the provider surface is gone; while the app is backgrounded after a click, keep the slot `showing`. If a last-resort diagnostic cap is retained, it must not dispose, transition, call the completion, or refill until foreground plus provider-overlay absence is established.

## 4. UNVERIFIABLE — Real Android/iOS provider parity and offline/flapping recovery

The Dart bridges expose AppLovin app-open/interstitial/rewarded calls on both platforms (`lib/src/adapters/applovin_bridge.dart:48-113`) and the reconnect path debounces an offline-to-online transition, refills fullscreen slots, nudges widget formats, and bumps `initRevision` so mounted widgets retry (`lib/src/core/ad_manager.dart:5500-5547`). Static source and fake-bridge tests cannot prove that the current native plugin versions deliver the assumed callback ordering, lifecycle transitions, ATT presentation behavior, app-open behavior, or native-view destruction on real Android and iOS devices under network loss.

Evidence that would settle this: a release-mode device matrix covering one Android device and one physical iPhone for each provider, with (a) cold start offline then reconnect, (b) network loss during each load, (c) airplane mode during each fullscreen show and during click-out/return, (d) two complete load/show/dismiss/refill cycles per fullscreen format, (e) provider switching followed by the same cycles, and (f) Instruments/Android Studio heap checks after repeated banner/native mount-unmount and provider-switch loops. The focused fake-bridge/state tests run during this audit passed (102 tests), but they cannot substitute for that evidence.

## Score and verdict

**Score: 4/10.**

**Verdict: Not safe for production use until rewarded completion/accounting and the app-open displayed-ad hard-cap lifecycle are corrected and the real-device matrix passes.**
